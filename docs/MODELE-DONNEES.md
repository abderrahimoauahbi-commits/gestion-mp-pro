# Gestion MP PRO — modèle de données

Document de réalisation : le schéma PostgreSQL 16 de Gestion MP PRO, table par table, avec la
correspondance de chaque table et de chaque colonne de Gestion MP (`docs/heritage/DONNEES.md`,
49 tables, 405 colonnes) et le traitement de chacune de ses 37 incohérences. Il fait foi pour
`backend/gestion_mp_pro/modeles/` et pour la migration Alembic initiale. Tout écart entre le code
et ce document se corrige dans le document **avant** le code.

Sommaire : 1. Principes · 2. Énumérations · 3. Tables (socle, référentiels, stock, achats,
production, opérations, inventaire, importations, suivi, reprise) · 4. Ce qui sortait du journal
et du texte · 5. Correspondance Gestion MP → PRO · 6. Incohérences de DONNEES.md et leur
traitement · 7. Invariants · 8. Index · 9. Migrations · 10. Reprise depuis `gestion_mp` ·
11. Chiffres.

## 1. Principes

### 1.1 Types

| Catégorie | Type PostgreSQL | Exemples | Règle |
|---|---|---|---|
| Quantité de matière (kg) | `NUMERIC(14,3)` | `mouvement.quantite`, `solde.quantite`, pesées, commandé | Au gramme. « Sous le gramme, c'est zéro » devient exact : plus de poussière flottante (`POUSSIERE` reste la constante du moteur, 0,001). |
| Prix unitaire | `NUMERIC(18,6)` | `matiere.prix`, `commande_ligne.prix`, `mouvement.prix` | Au millionième (un prix au mètre de 0,0011 USD garde ses chiffres). |
| Montant | `NUMERIC(16,2)` | `facture.montant`, `dossier_frais.montant`, `commande.montant_approuve` | Au centime, dans la devise de la ligne ou en MAD (dit par le nom : `_mad`). |
| Cours de change | `NUMERIC(14,6)` | `devise.cours`, `mouvement.cours`, `commande.cours` | MAD pour 1 unité de devise. **NULL = pas de cours figé** (fin des « trois sens du zéro »). |
| Taux (fraction) | `NUMERIC(9,6)` | `code_douanier.taux_droits`, `inventaire.tolerance`, `ordre.taux_perte_fige` | 0,02 = 2 %. |
| Pourcentage 0–100 | `NUMERIC(9,6)` | `recette.pourcentage`, `montage.pourcentage` | Part dans un rôle, part d'un fil sur un étage. |
| Mesure fine | `NUMERIC(14,6)` | densité (kg/ml), poids de bobine (kg), poids au m² (kg/m² ou ml/m²) | Mesures, pas des stocks. |
| Compte d'unités | `NUMERIC(12,3)` | palettes, bobines | Une palette peut être entamée. |
| Surface | `NUMERIC(14,3)` | m² d'un ordre, base mensuelle du plan | |
| Coefficient | `NUMERIC(8,4)` | saisonnalité (0–20) | |
| Jours | `INTEGER` | délais fournisseur, délai de paiement | Gestion MP les avait en `FLOAT` (incohérence 35). |
| Date d'un fait | `DATE` | `date_effet`, `date` d'un document | Jour de l'usine (Africa/Casablanca). |
| Instant | `TIMESTAMPTZ` | `cree_le`, `valide_le`, `quand` | Stocké en UTC, présenté à l'heure de Casablanca (`services/horloge.py`). |
| Texte borné | `VARCHAR(n)` | | Les longueurs de l'API (Pydantic) sont **dérivées** de celles du modèle (incohérence 21) : une même constante. |
| JSON | `JSONB` | `journal.avant/apres`, `notification.donnees` | Jamais pour une donnée métier relue par un calcul. |

**Calcul** : la base garde des `Decimal` exacts ; le chargeur du moteur (`services/donnees_moteur.py`)
les convertit en `float` et le moteur calcule en `float` comme Gestion MP (parité). Les **écritures**
(stock, montants, parts) se calculent en `Decimal` et s'arrondissent **une fois**, à l'écriture,
avec `ROUND_HALF_UP` à l'échelle de la colonne (`modeles/types.py : arrondir(valeur, categorie)`).
L'affichage arrondit selon la règle unique de `ARCHITECTURE.md` § 9.3.

**Pas de NaN** : en PostgreSQL `'NaN' >= 0` est vrai, si bien qu'un `NaN` passerait tous les CHECK
de bornes. **Chaque** colonne `NUMERIC` (hors colonne générée) porte donc un CHECK
`ck_<table>_<colonne>_nombre` : `<colonne> <> 'NaN'` (74 CHECK, posés par
`base.completer_le_schema`, écrits en clair dans la révision 0001 ; étape 18 de Gestion MP
corrigé, généralisée). L'infini est refusé par PostgreSQL lui-même (`NUMERIC(p,s)`) ; côté
Python, `arrondir()` refuse NaN, l'infini et toute valeur hors de la colonne.

### 1.2 Conventions de nommage et de structure

- Tables au singulier, en français, en `snake_case` ; clés `id` ; clés étrangères `<table>_id`.
- Convention de nommage des contraintes déclarée sur `MetaData` (`modeles/base.py`) :
  `pk_%(table_name)s`, `fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s`,
  `uq_%(table_name)s_%(column_0_N_name)s`, `ck_%(table_name)s_%(constraint_name)s`,
  `ix_%(table_name)s_%(column_0_N_name)s`. Tout CHECK porte un nom parlant (`ck_mouvement_quantite_non_nulle`),
  toujours de la forme `ck_<table>_<nom>` (nom de **table** entier : `ck_role_nomenclature_…`,
  `ck_poste_frais_…`, `ck_piece_jointe_…`). Les CHECK génériques — valeurs d'une énumération
  (`…_enum`) et refus de NaN (`…_nombre`) — sont posés par `base.completer_le_schema`.
- Identifiants : `INTEGER GENERATED BY DEFAULT AS IDENTITY` ; `BIGINT` pour `mouvement`, `journal`,
  `notification`. « By default » permet à la reprise de **garder les identifiants** de Gestion MP
  (parité ligne à ligne, § 10), puis de recaler les séquences.
- Colonnes communes des documents et fiches modifiables : `version INTEGER NOT NULL DEFAULT 1`
  (verrou optimiste, `version_id_col` de SQLAlchemy : tout `UPDATE` vérifie et incrémente),
  `cree_le TIMESTAMPTZ NOT NULL DEFAULT now()`, `cree_par_id`, `modifie_le`, `modifie_par_id`.
- **Utilisateurs par id** : toute colonne « qui » est une clé étrangère vers `utilisateur.id`
  (`*_par_id`, `auteur_id`). Le nom affiché se lit par jointure ; seul `journal.utilisateur_nom`
  garde une copie (le journal reste lisible même si le nom change).
- **Devise** : toujours `CHAR(3)` clé étrangère vers `devise.code`.
- **Défauts** : tout défaut est **aussi** un défaut serveur (`server_default`) : une insertion SQL
  hors ORM (reprise, outils) obtient les mêmes valeurs (incohérence 28).
- **Suppressions** : `ON DELETE CASCADE` seulement pour les lignes d'un document (lignes, parts,
  poids, saisons, versions et décisions d'un bon — un brouillon renvoyé reste supprimable, le
  journal garde la trace —, montages d'un étage), pour les sessions d'un compte et les lectures
  d'une notification ; partout
  ailleurs `RESTRICT` (rien ne disparaît en silence). Pas de
  `ON UPDATE CASCADE` : les référentiels ont une clé technique `id`, leur `code` se renomme sans
  toucher aux matières (incohérence 22 réglée par construction).
- **Rien de métier ne se supprime physiquement une fois validé** : documents validés, mouvements,
  soldes, journal, versions, lots. Les brouillons se suppriment ; un inventaire ou un dossier
  numéroté s'**abandonne** / s'**annule** (statut), pour ne pas laisser de trou dans sa série.

### 1.3 Énumérations

Chaque énumération est une `StrEnum` Python (`modeles/enums.py`) mappée par
`types.enumeration(classe, n)` = `sqlalchemy.Enum(..., native_enum=False, create_constraint=False, length=n)` :
colonne `VARCHAR(n)` **et** CHECK nommé `ck_<table>_<colonne>_enum`, posé par
`base.completer_le_schema` (pas par le type : la révision le porte en clair, indépendante de la
convention de nommage du moment ; 41 colonnes énumérées). Pas de type `ENUM` natif
(une valeur ajoutée = une migration simple `DROP/ADD CONSTRAINT`). Les valeurs sont celles de la
base de Gestion MP quand elles existent (parité, reprise sans traduction), sauf les statuts
harmonisés en § 2 (table de traduction appliquée par la reprise).

### 1.4 Recherche sans accents

Les tables cherchées « à la frappe » (matière, fournisseur, lot, commande, réception, dossier,
qualité, ordre) portent `texte_recherche TEXT NOT NULL DEFAULT ''` (minuscules, sans accents, tous les
champs cherchables concaténés, tenu par l'écouteur `before_flush` de `modeles/recherche.py`, dont
`normaliser()` est la règle unique, la même que l'écran ; une écriture SQL directe — la reprise —
appelle ensuite `recherche.recalculer_table(session, Modele)`) avec un index GIN
`gin_trgm_ops` (extension `pg_trgm`, créée par la migration 0001). La règle « tous les mots,
dans n'importe quel ordre » s'écrit `texte_recherche LIKE '%mot1%' AND … LIKE '%motN%'`, mots
échappés (`%` et `_` littéraux).

### 1.5 Audit

`journal` reçoit, dans la **même transaction** que le geste, une ligne par geste métier avec
`avant` / `apres` (JSONB) calculés automatiquement par l'écouteur `services/audit.py`
(`before_flush` : attributs modifiés de chaque objet suivi ; les colonnes de prix sont gardées —
le journal n'est lisible que par la direction et l'administrateur, et l'historique d'une fiche
passe par le filtre des prix). L'historique d'une fiche = `journal WHERE objet = ? AND objet_id = ?`.

## 9. Migrations (Alembic)

- Dossier `backend/gestion_mp_pro/migrations/` (`env.py`, `script.py.mako`, `versions/`), configuration
  dans `backend/alembic.ini` ; l'URL vient de `config.Reglages().base`.
- Révisions **linéaires** nommées `NNNN_<objet>.py` avec `revision = "NNNN"` (identifiants
  numériques contigus `0001`, `0002`…, `down_revision` = la précédente). Jamais modifiée une fois livrée.
- `0001_schema_initial` : extension `pg_trgm`, toutes les tables de § 3, contraintes (CHECK `…_enum` et
  `…_nombre` compris, en clair), index, triggers (`tr_mouvement_immuable`, `tr_operation_type_fige`,
  `tr_matiere_lineaire_densite`) : DDL écrit en clair, sans import du paquet.
- `0002_semences` : rôles de nomenclature (8, `de_base`), postes de frais (11, natures), devises
  (MAD 1 ; USD 10 ; EUR 10,8), magasins (« Magasin principal » `stock_courant`, « Quarantaine »,
  chacun seulement si aucun magasin de son type n'existe), 16 motifs (§ 3.2.12), **56 réglages** à
  leur défaut (§ 3.1.6 : les réglages de Gestion MP corrigé dont `delai_frais_import_jours` = 30, et
  `seuil_bc_urgent` = 300 000 gardé pour mémoire ; `modifie_par_id` NULL) ; `INSERT … ON CONFLICT DO NOTHING`
  (rejouable, n'écrase rien). Données écrites **en dur dans la révision** (pas d'import du paquet).
- `0003_tolerance_tva_import` : le réglage `toler_tva_import` (défaut 0,05, bornes 0–1 ; C29 et fiche du dossier),
  ajouté à Gestion MP corrigé après S1 — clé dans `CLES_REGLAGES`, CHECK `ck_parametre_cle_connue`
  remplacé (`DROP`/`ADD`), semence `ON CONFLICT DO NOTHING` ; 57 réglages ensuite. Le retour arrière efface la clé et son historique.
- `0004_versions_et_genres` (lots D1 et D10) : `role_nomenclature.version` (défaut 1) ; `OrigineCours` +
  `periode_close` ; `GenreSauvegarde` + `avant_vidage`, `avant_mise_a_jour` (CHECK `…_enum` remplacés).
  Le retour arrière range `periode_close` en `saisi` et retire du registre les sauvegardes des deux genres
  (leurs fichiers restent : le disque fait foi).
- Les révisions suivantes : une par changement, avec `upgrade()` et `downgrade()`, numérotées à la suite
  (numéro réservé auprès du coordinateur), relues après autogénération : autogenerate ne voit ni les
  CHECK modifiés ni les déclencheurs (à écrire à la main) ; pas de `%` dans le texte d'un CHECK (utiliser `~`).
- Démarrage : `services/installation.migrer()` appelle `alembic upgrade head` sous
  `pg_advisory_lock(7426201)` (un seul processus migre ; les autres attendent puis vérifient
  `head`). L'application refuse de servir si la base n'est pas à `head` (`/api/sante` → `schema: "en retard"`).
- Essais (`tests/test_migrations.py`) : identifiants contigus de 0001 à N ; `upgrade head` sur base
  vide puis relancé = rien ; `downgrade base` puis `upgrade head` ; schéma migré = métadonnées des
  modèles (`alembic check` vide) ; deux processus simultanés : une seule application ; aucune révision
  n'importe `gestion_mp_pro`.

## 10. Reprise depuis la base `gestion_mp` (lecture seule)

Module `backend/gestion_mp_pro/reprise/` ; commande `python -m gestion_mp_pro.reprise
--source postgresql+psycopg:///gestion_mp --mode referentiels|activite|tout [--remplacer-activite] [--mettre-a-jour] [--essai]
[--cible URL] [--pieces-source DOSSIER] [--rapport FICHIER] [--genre gestion_mp|erp_fil]`.
`--date-limite` n'est **pas** fait (lot R1) : reprendre une activité tronquée casserait soldes et documents.
`outils/vider_activite.py` sauvegarde d'abord (`avant_vidage`), retire de la table les pièces jointes
des documents mais **garde leurs fichiers**, puis sauvegarde la base vide (`reference_vide`).

### 10.1 Garde-fous

- La source est ouverte en `default_transaction_read_only = on` et `SET TRANSACTION ISOLATION LEVEL
  REPEATABLE READ READ ONLY` : une seule photo cohérente, aucune écriture possible. Empreinte de
  la source (comptes de lignes + `MAX(id)` + somme de contrôle par table) relevée avant et après.
- La cible refuse une base qui ne s'appelle pas `gestion_mp_pro`, `gestion_mp_pro_*` ; sauvegarde
  `avant_reprise` de la cible faite d'abord.
- Rejouable : `reprise_correspondance` ; un second passage sans changement source ne crée rien.
  `--mode activite` exige des référentiels repris. Une base cible dont l'activité a été saisie
  **dans PRO** refuse la reprise d'activité (sinon deux vérités) sauf `--remplacer-activite`, qui
  vide l'activité PRO (sauvegarde faite) puis reprend.

### 10.2 Normalisation (une seule fois, à l'entrée)

Toute valeur flottante de Gestion MP est arrondie à l'échelle de sa colonne PRO (§ 1.1),
`ROUND_HALF_UP`. Les **soldes** ne sont pas lus : ils sont **recalculés** = Σ des mouvements
arrondis (C12 tenu par construction). Les parts de frais sont réparties aux plus forts restes.
Le rapport de reprise donne, par table et par colonne, le nombre de valeurs arrondies et l'écart
maximal (ex. « mouvement.quantite : 412 valeurs arrondies, écart max 0,0004 kg »).

### 10.3 Correspondances de valeurs

| Source | Règle |
|---|---|
| Noms d'utilisateur (`cree_par`, `auteur`, `par`…) | rapprochés des comptes par `lower(trim(nom))` ; un nom inconnu crée un compte `historique` (inactif, sans rôle) ; « système », « installation », « reprise ERP Fil » → NULL ; le rapport liste les rapprochements (« Mohamed », « MOHAMED » → même compte : signalé, pas fusionné en silence si deux comptes existent) |
| Codes de classification, rôles, postes, codes douaniers | → `id` par le code |
| `magasin.type` | `Stock courant` → `stock_courant`, `Quarantaine` → `quarantaine` |
| `mouvement.document` | `sortie` → `ordre` |
| `document_id` | vers la FK typée |
| `motif` (texte) | libellé connu → `motif_id` ; sinon `motif_texte` |
| `cours = 0`, `montant_approuve = 0`, `facture.montant = 0` | NULL |
| `LOT INTERNE` | `lot_interne = true` |
| `version_approuvee` (JSON) | une `commande_version` (motif `reprise`, `figee_le` = `approuvee_le` sinon `cree_le`) |
| `theorique` (JSON) | `ordre_prevu` (référence → id ; une référence introuvable est signalée), `taux_perte_fige` |

| Journal « renvoi aux achats », « commande à approuver », « approbation commande », « version partie rétablie »… | `commande_decision` (motif = partie après « · ») |
| Journal « annulation réception » | `annulation_motif`, `annulee_le`, `annulee_par_id` |
| Journal « montage » | `montage_evenement` (texte en `alerte` si non interprétable) |
| Journal | repris tel quel (`utilisateur` → id + nom gardé), `avant/apres` NULL |
| Inventaire ouvert dans la source | repris **ouvert** en mode `activite` (les deux logiciels montrent la même chose) ; signalé au rapport |
| Pièces jointes | fichiers **copiés** (jamais déplacés) de `~/gestion-mp-pieces/` vers le dossier PRO, empreinte vérifiée, chemin relatif |
| Compteurs | `compteur` recalé au plus grand numéro repris par (série, année) |
| Séquences | `setval` de chaque identité sur `MAX(id)` |

### 10.4 Contrôle de reprise

Le rapport (`reprise_execution.rapport`, et `essais/resultat-reprise.txt`) commence par : comptes
de lignes par table source/cible ; Σ quantités et Σ quantité × prix du journal par matière ;
soldes = journal ; mêmes numéros de documents ; mêmes recettes et plans versionnés (empreintes) ;
liste des valeurs signalées (données réelles douteuses, **signalées, jamais corrigées**, M11).

### 10.5 Corrections déclarées (écarts voulus avec Gestion MP)

Toute différence de comportement ou de chiffre entre PRO et Gestion MP est l'une des suivantes,
chacune avec sa règle d'explication dans `outils/comparer_avec_gestion_mp.py` et son essai :

| # | Correction | Effet observable |
|---|---|---|
| K1 | Arrondi des valeurs à l'échelle des colonnes (§ 10.2) | écarts ≤ 0,001 kg / 0,01 MAD par valeur ; la règle recalcule l'écart attendu depuis la source |
| K2 | Inventaire limité à son périmètre (§ 6 n° 38) | un mouvement hors périmètre accepté par PRO, refusé par GMP |
| K3 | Inventaire abandonné / dossier annulé gardés | lignes en plus avec statut `abandonne` / `annule`, absentes des calculs |
| K4 | Réception entièrement refusée annulable | GMP 409, PRO accepte |
| K5 | `controle_par` lu comme contrôleur qualité | identique tant que `controle_par` est vide |
| K6 | Alimentation : plus de réglages ni de cours | 403 chez PRO, 200 chez GMP |

Aucune autre différence n'est admise (règle de `PLAN-DE-RECETTE-PRO.md` § 7.6).
