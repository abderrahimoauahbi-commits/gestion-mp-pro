# Lot R2 — parité de calcul PRO = Gestion MP sur l'année d'essai : ce que les lots suivants doivent savoir

Branche `lot-R2`. Critère A6 tenu : **à corriger : 0** (`backend/essais/resultat-parite.txt`).
`make verifier` vert (pytest 2 595 + 13 essais de R2 ; l'essai complet de R2 vert avec
`GESTIONMPPRO_ESSAIS_COMPLETS=1`, ≈ 5 min). Gestion MP calculé : `c1133ba` ; PRO : `e5d5cc5` + R2.

## 1. Lancer

```
cd backend
GESTIONMPPRO_PARITE_PREFIXE=gestion_mp_pro_<lot> .venv/bin/python essais/parite_gestion_mp.py \
    [--sortie FICHIER] [--passes statique,api,dynamique,k7] [--garder]
make parite            # préfixe par défaut gestion_mp_pro_parite
```

Bases d'essai créées et **supprimées** à la fin : `<préfixe>_source_essai` (copie de
`gestion_mp_comparaison`, pg_dump en lecture), `<préfixe>_cible_essai` (reprise R1),
`<préfixe>_traduite_essai` (chaîne en base), `<préfixe>dyn_*` (dynamique), `<préfixe>k7_*` (K7).
Serveurs sur des ports libres > 8100 (Gestion MP : son interpréteur, son code en lecture seule,
sauvegardes et pièces dans un dossier temporaire ; PRO : ce dépôt), toujours arrêtés (`with`).
Empreintes de `gestion_mp` et `gestion_mp_comparaison` relevées avant/après : identiques.
Comptes d'essai : une ligne `utilisateur` + une session écrite à la main dans chaque base d'essai
(aucun code saisi).

## 2. Méthode (forme et ampleur, aucune excuse en bloc)

| Passe | Fichiers | Ce qui est prouvé |
|---|---|---|
| Données | `parite_donnees.py` | Les `Donnees` du chargeur PRO = celles du dépôt de Gestion MP, à des traductions près, chacune reconnue par une règle qui vérifie la valeur ; la chaîne D0 → D1 → … redonne **exactement** les données de PRO |
| Statique | `parite_statique.py`, `gestion_mp_parite.py` (interpréteur de Gestion MP) | 19 dates (12 fins de mois + 08/10 + six 15 du mois : aucune version de plan ni de recette ne change dans l'année) ; moteur PRO = moteur de Gestion MP **à l'égalité exacte** sur les mêmes données ; chaque écart PRO/Gestion MP expliqué par la première traduction dont le recalcul par Gestion MP redonne la valeur de PRO |
| API | `parite_api*.py`, `parite_chaine_base.py`, `parite_serveurs.py` | 155 paires de routes (pilotage aux 19 dates, bilans de 13 mois, 11 routes de documents, fiches comprises) traduites champ à champ ; écarts expliqués par **le code de Gestion MP rejoué** (son dépôt remplacé par les jeux traduits ; rejeu sur D0 = réponse du serveur, vérifié), puis par une **chaîne en base** (copie de Gestion MP où chaque traduction de la reprise est refaite, serveur relancé) ; règle directe K3 ; écrans de l'alimentation |
| Dynamique | `parite_dynamique*.py` | 22 gestes joués dans les deux (réception facturée en USD, ordre, retour machine, sortie refusée, inventaire avec écart, dossier clos, réception refusée annulée, K2, K3) : même issue, même message de refus, mêmes numéros, même document, même changement de stock / valorisation / lots |
| K7 | `parite_k7.py` | Copie montée (2 fils), reprise : ce que le montage change chez PRO = ce que Gestion MP rejoué avec le montage connu aux dates passées change |
| Rapport | `parite_rapport.py`, `parite_gestion_mp.py` | par passe et section : comparées, expliquées par classe (ampleur max), à corriger ; réciproque (champs de Gestion MP rendus ailleurs, avec leur raison) |

## 5. Défauts de Gestion MP signalés (ne pas toucher ~/gestion-mp ; à corriger en service)

   une date passée, la piste d'économie compare des prix futurs (ex. au 15/05/2026 : prix du
