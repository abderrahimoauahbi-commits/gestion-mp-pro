Une fois installés, on les appelle de préférence depuis `…/Gestion MP PRO/outils/` (ce que font
le raccourci et l'agent). Les variables sont celles d'ARCHITECTURE § 16 ; deux de plus, propres
aux scripts : `GESTIONMPPRO_PROJET` (le dépôt à figer) et `GESTIONMPPRO_APPLI` (dossier de
l'application : sert aux essais pour s'installer à part ; une installation le déduit de
l'emplacement de ses outils).

## 3. Décisions

1. **Démarrage automatique laissé au choix du Mac** (consigne du lot, comme pour Gestion MP) :
   `installer.sh` ne pose l'agent qu'avec `--demarrage-automatique`. Éprouvé sous une étiquette
   d'essai puis retiré (RunAtLoad, relance après `kill -TERM` et `kill -KILL`, `arreter.sh`
   le suspend sans relance, `--retirer` le retire et rend le port). L'agent n'écrit que la base, le
   port et les réglages **donnés à l'appel** (jamais les défauts ni le fichier « environnement »,
   relus à chaque démarrage ; jamais de secret dans le plist).
2. **Outils du poste installés à part** du dépôt : le raccourci et l'agent ne dépendent ni d'un
   worktree ni de l'état de `main` ; changer `deploiement/mac` ou `scripts/` demande de relancer
   `installer.sh` (idempotent).
3. **Copie figée refaite seulement si le commit change** (Gestion MP la refaisait à chaque
   démarrage) : une relance par launchd ou le raccourci est immédiate ; `--refaire` force. Une copie
   ne se remplace jamais sous un serveur en marche. Avant de servir **une autre version** que la
   précédente : sauvegarde « avant mise à jour » faite avec le code de la nouvelle copie ; si elle
   échoue, l'ancienne version reste en place.
4. Écran du commit construit dans un dossier à part avec les modules du projet (si
   `package-lock.json` est identique), sinon `npm ci` à part.
5. **Un seul processus uvicorn** sur le Mac (`GESTIONMPPRO_PROCESSUS` le change) ; écoute
   `127.0.0.1` (Gestion MP écoute `0.0.0.0`) : pour l'atelier, `GESTIONMPPRO_ECOUTE=0.0.0.0` dans
   le fichier « environnement », avec HTTPS (X3, ARCHITECTURE § 5.4).
6. `arreter.sh` n'arrête qu'un processus `gestion_mp_pro.main:app` qui écoute sur le port de
   PRO ; s'il y trouve autre chose, il le dit et ne touche à rien. Il ne décharge l'agent que si
   celui-ci sert ce port (un agent d'essai ne touche pas la production).
7. `restaurer.sh` exige **le serveur de cette base arrêté** (serveur en marche : restaurer depuis
   l'écran, Administration › Sauvegardes, qui restaure dans le processus) — sinon le processus
   serveur garderait son état de schéma ; fichier pris dans le dossier de la base seulement ;
   confirmation `RESTAURER` (question au terminal, ou `--confirmation`). Il appelle
   `services.restauration.preparer/executer` (D10) avec un auteur technique « poste Mac
   (scripts) » sans compte : sauvegarde « avant restauration » sans auteur, toutes les sessions
   fermées, journal « restauration » au nom du poste dans la base restaurée.
8. `sauvegarder.sh` (manuelle) écrit aussi sa ligne au journal (« sauvegarde », au nom du poste),
   comme le geste de l'écran ; la copie externe est exigée pour la manuelle seulement.
9. Rôle `gestion_mp_pro` **sans mot de passe** : `pg_hba` de Homebrew est en `trust` local et
   PostgreSQL n'écoute que la machine. Un serveur PostgreSQL exposé demanderait un mot de passe
   (`GESTIONMPPRO_BASE` avec mot de passe, `pg_hba` en `scram-sha-256`) : à décrire par X3.
10. `umask 077` pour tout ce qu'écrivent les scripts du poste (sauvegardes, pièces, journaux).

## 4. Écarts aux documents (à reporter par le coordinateur)

- ARCHITECTURE § 13.2 et LOTS X2 « `installer.sh` … installe le LaunchAgent » : seulement avec
  `--demarrage-automatique` ; § 14.1 ligne « Démarrage » : **double-clic** tant que l'utilisateur
  du Mac n'a pas installé l'agent.
- § 13.2 « `.venv` » : l'installation n'utilise pas `backend/.venv` du projet (environnement de
  développement) mais un environnement par `requirements.lock` dans `Application Support`.
- § 14.1 ligne « Rôle PostgreSQL » : `CONNECT` sur `gestion_mp` reste ouvert à `PUBLIC` (défaut
  de PostgreSQL, réglage de la base de Gestion MP auquel PRO ne touche pas) ; le rôle n'y possède
  rien et n'y a reçu aucun droit (vérifié par `pg_shdepend`, sans se connecter à `gestion_mp`) et
  ne s'y connecte jamais (vérifié par `pg_stat_activity`). Inversement `CONNECT` est retiré à
  `PUBLIC` sur `gestion_mp_pro`.
- § 14.1 « Journal du serveur `~/Library/Logs/Gestion MP PRO/` » : trois fichiers (§ 1).
- Fichiers d'essai en plus de `essais/coexistence.sh` : `essais/demarrage_automatique.sh`,
  `essais/sauvegarde_restauration.sh` et leurs `essais/resultat-*.txt`.
- `make` n'a pas de cible du poste (Makefile à S0) : proposer `poste-installer` →
  `deploiement/mac/installer.sh`, `coexistence` → `essais/coexistence.sh`.

## 5. Pour les autres lots

- **C1** : les deux serveurs se démarrent côte à côte (raccourci, ou
  `…/outils/demarrer.sh`) ; `/api/sante` de PRO dit le commit servi (`version`). Le miroir : `make
  miroir` depuis `~/gestion-mp-pro` vise la base installée (adresse par défaut, rôle
  `gestion_mp_pro`) avec le code **du projet** ; après une reprise faite hors du serveur, le
  cache du moteur se recale par sa signature (R1). Base vide de référence pour revenir avant le
  miroir : `scripts/restaurer.sh gestion-mp-pro-…-reference-vide.dump` (serveur arrêté).
- **X3** (EXPLOITATION.md) : reprendre § 1–3 ; la mise à jour de version = arrêter, double-clic
  (copie refaite, sauvegarde « avant mise à jour », migration au démarrage) ; changer les scripts
  du poste = relancer `installer.sh` ; essai de restauration mensuel = `essais/
  sauvegarde_restauration.sh` sur une base d'essai ; vérifier la coexistence =
  `essais/coexistence.sh` (il remet PRO dans l'état trouvé).
- **V3/V4** : 8050 sert l'écran construit de la copie ; pour un essai, une autre base et un autre
  port (`GESTIONMPPRO_BASE`, `GESTIONMPPRO_PORT`) donnent une autre copie (`version-<base>`).
