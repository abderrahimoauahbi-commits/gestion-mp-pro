# Lot X1 — Serveur : Docker Compose, Caddy, systemd

Branche `lot-X1` (main fusionnée). Déploiement SERVEUR de Gestion MP PRO : une image unique
(écran compilé servi par l'API Python), PostgreSQL 16, Caddy en HTTPS, et une variante systemd
sans Docker. Inspiré fortement de GMAO PRO (`~/gmao-pro/deploiement`, même usine, même famille).

## ⚠️ Ce qui N'A PAS pu être fait ici (reste À FAIRE sur une machine Linux avec Docker)

Docker n'est pas installé sur ce Mac (pas de `docker`, pas de VM Linux, `docker compose config`
indisponible). Les fichiers sont écrits, relus et vérifiés autant que possible SANS Docker (voir
« Ce qui est vérifié ici »). **Les trois critères de LOTS X1 qui demandent Docker restent à
faire et NE sont PAS cochés :**

1. **Image construite** (`docker compose -f deploiement/docker-compose.yml build`, ou `make docker`).
2. **`docker compose up` sur une machine propre** : base, application (2 processus, non root,
   `HEALTHCHECK` vert), Caddy HTTPS (`tls internal`) ; migration au démarrage ; sauvegarde
   quotidienne écrite dans le volume ; copie externe montée ; `docker compose down && up` sans
   perte ; CSP sans erreur dans la console à travers Caddy (recette V3).
3. **Service systemd essayé sur une VM Linux** (`systemctl enable --now gestion-mp-pro`).

## 3. Décisions (documents muets ou à préciser)

1. **La CSP reste à l'application** (S0 n° 8, D9 décision 4, RESTES « D9 → X1 ») : Caddy ne pose
   que HSTS et Permissions-Policy au bord ; il **laisse passer** la CSP de l'application et celle,
   propre à chaque document imprimable, qui autorise le bouton « Imprimer » par l'empreinte
   sha256 de son script (`documents/rendu.py`). L'application pose déjà `X-Content-Type-Options`,
   `X-Frame-Options`, `Referrer-Policy` : Caddy ne les redouble pas. GMAO PRO, lui, posait une CSP
   dans son Caddyfile — ici c'est volontairement **retiré**.
2. **Fuseau** : PostgreSQL reçoit `timezone`/`log_timezone` = `GESTIONMPPRO_FUSEAU` ; l'application
   reçoit `GESTIONMPPRO_FUSEAU` (zoneinfo). **Pas de variable `TZ`** passée au processus de
   l'application (C16, `config.py`) — différence avec GMAO PRO qui posait `TZ`.
3. **Deux processus par variable** : `CMD` en `sh -c "exec uvicorn … --workers
   ${GESTIONMPPRO_PROCESSUS:-2}"` (et `--port ${GESTIONMPPRO_PORT:-8050}`), pour honorer
   `GESTIONMPPRO_PROCESSUS`/`_PORT` sans réécrire le Dockerfile ; `exec` pour qu'uvicorn soit
   PID 1 et reçoive les signaux. Chaque worker rejoue le `lifespan` : migration sérialisée par le
   verrou MIGRATION, tâches portées par un seul (verrou TACHES) — par conception (D10 § 8).
4. **Pièces jointes** : un volume `pieces` en plus des `sauvegardes` (l'application a des pièces,
   `GESTIONMPPRO_PIECES`), dossier `700` au seul compte. GMAO PRO n'avait que `sauvegardes`.
5. **Copie externe** : montage **commenté** dans le compose (`/copie`), à activer par l'exploitant
   avec `chown 10001:10001` et `GESTIONMPPRO_SAUVEGARDES_COPIE=/copie` (D10 § 2 n° 4).
6. **Version servie** : `ARG VERSION` écrit dans `/app/VERSION` (lu par `api/systeme/routes.
   version_servie`, `RACINE=/app`) ; passé par `GESTIONMPPRO_VERSION` du `.env`. Sans lui,
   `/api/sante` affiche « 0.1.0 (projet) ».
7. **Compte** `gestionmppro` (GMAO PRO : `gmaopro`), uid/gid 10001 identiques pour que le `chown`
   de la copie externe soit documenté d'avance.
8. **`.env` seulement pour Compose** : l'application ne lit aucun `.env` (S0 n° 11) ; Compose lit
   `--env-file .env` et passe les variables par `environment`. Le fichier systemd lit
   `/etc/gestion-mp-pro.env` (droits 600).

## 5. Coexistence avec Gestion MP et le poste Mac (X2)

- Le **serveur** (Docker/systemd) et le **poste Mac** (X2, déjà fait, non retouché) sont deux
  déploiements distincts : on n'installe PAS les deux sur la même machine. Sur le Mac de l'usine,
  c'est X2 (double-clic/launchd, base `gestion_mp_pro`, port 8050, 127.0.0.1) ; sur un serveur,
  c'est X1 (Docker ou systemd, Caddy en façade).
- Gestion MP (8030) n'est pas concerné par X1 (il tourne sur le Mac). Si un jour X1 et Gestion MP
  cohabitaient sur un même hôte, seuls 80/443 de Caddy sont publiés ; aucun partage de base, de
  cookie (`gestion_mp_pro_session`) ni de verrou (7426201–7426209).

## 6. À faire ensuite (sur Linux + Docker)

1. `cp deploiement/exemple.env .env` puis remplir `GESTIONMPPRO_NOM`, `GESTIONMPPRO_MOT_DE_PASSE_BASE`.
2. `make docker` (construit l'image) puis `docker compose -f deploiement/docker-compose.yml
   --env-file .env up -d --build`.
3. Vérifier : `docker compose ps` (application `healthy`), `curl -k https://<nom>/api/sante`,
   console du navigateur sans erreur CSP, bouton « Imprimer » d'un bon fonctionnel, sauvegarde du
   jour dans le volume, `down && up` sans perte.
4. Variante systemd : copier le projet dans `/opt/gestion-mp-pro`, `/etc/gestion-mp-pro.env`
   (600), `systemctl enable --now gestion-mp-pro`, Caddy local (`reverse_proxy 127.0.0.1:8050`).
5. Reporter le résultat dans X3 (`docs/EXPLOITATION.md`).
