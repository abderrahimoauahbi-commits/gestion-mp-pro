# Lot S3 — moteur de calcul pur : ce que les lots suivants doivent savoir

Branche `lot-S3`. Le moteur de Gestion MP (`gestion_mp/calcul/moteur.py`, `modele.py`,
`classification.py`, `controles.py`, les calculs purs de `depot.py` et ceux logés dans ses
routes) est porté **fonction par fonction** dans `backend/gestion_mp_pro/calcul/`, méthode
« corrigée » seule (P17). Code de Gestion MP porté : **f18b445** (identique à c28fafc pour le
moteur), puis le seul changement de moteur arrivé pendant le portage, **26459d4** (tolérance de
C29 réglable, retours A-30). À **c1133ba**, les sorties de Gestion MP sur les 20 jeux sont
inchangées.

Aucune base, aucune horloge : la date de référence (`date_ref`, `jour`) et la date du jour
(`aujourdhui`) sont **toujours** des paramètres. Fichiers ≤ 400 lignes, fonctions ≤ 60 lignes,
mypy strict, docstrings, constantes nommées (`constantes.py`).

## 1. Forme des `Donnees` (`calcul/modele/`)

Les dataclasses portent **les mêmes champs, dans le même ordre, avec les mêmes défauts** que
`gestion_mp/calcul/modele.py` (CALCULS A § 1), à deux différences près :

- `Parametres` n'a plus `methode` ni `mode_classeur` (la branche « classeur » n'existe plus) ;
  il a `toler_tva_import` (5 %, Gestion MP 26459d4) ;
- `Donnees.derniere_date` (hors constructeur) mémorise la dernière date écrite (`a_la_date`) ;
  les index `article()`, `fournisseur()`, `qualite()` sont recalculés par `__post_init__`
  (et `reindexer()` après une modification des listes en place).

Clés textuelles du moteur (affichage) : référence, code de qualité, nom de fournisseur, code de
magasin, numéro de bon, de lot, d'ordre. Les quantités sont des `float` en **kg** ; les
montants en devise de la pièce, `_mad` en dirhams. Rappels de traduction pour le chargeur (S4),
tous dans `calcul/chargement.py` en fonctions pures :

| Base PRO | Moteur | Fonction |
|---|---|---|
| statut du bon (brouillon, à approuver, envoyée…) | « Brouillon », « Envoyée », « Confirmée », « Soldée », « Annulée » ; un bon numéroté repassé par la direction reste parti | `statut_moteur(statut, numero, prix_confirmes)` |
| qualité d'une ligne reçue | « Conforme », « Réserve », « Refusé » | `QUALITE_MOTEUR` |
| type de mouvement (OUVERTURE…) | `STOCK_INITIAL`… ; quantité positive, signe porté par le type ; une annulation garde le type et a une quantité **négative** | `journal_du_moteur(list[EcritureLue])` |
| transfert = deux écritures appariées | une seule ligne, source → destination | idem |
| motif de retour (libellé) | code R1…R6 | `code_motif` |
| fournisseur d'un mouvement | celui du lot ; à défaut, celui de l'opération (A-30) | `EcritureLue.fournisseur_operation` |
| bon soldé à la main (journal « commande soldée ») | `Commande.solde_a_la_main_le` (sauf solde « tout reçu ») ; annulé : dernier « commande annulée » | `soldes_a_la_main` |
| reçu d'une ligne de bon | pesée des réceptions validées non refusées − retours au prorata des pesées du lot | `au_prorata`, `recu_par_ligne` |
| en quarantaine d'une ligne de bon | soldes des magasins « Quarantaine » au prorata | `au_prorata` |
| ligne de réception d'une entrée | appariement par (réception, lot) dans l'ordre, sinon (lot, date, pesée) | `lignes_des_receptions` |
| plan d'une qualité au journal | `VersionPlan` (seule une nouvelle base déplace l'origine de la croissance) ; qualité arrêtée sans histoire : jusqu'au mois de son dernier tissage | `versions_du_plan`, `arret_sans_histoire` |

Ce que `depot._charger` remplit et que S4 doit reproduire (voir CALCULS A § 4.6) :
`Commande.numero` = numéro sinon `BC-brouillon-{id}` ; `Reception.numero` = numéro sinon
`brouillon n° {id}` ; `Reception.numero_bc` = le bon unique de ses lignes, sinon vide ;
`LigneReception.tolerance_partielle` = réglage `toler_ecart_pesee` ; `LignePrix` = une par
ligne reçue validée, non refusée, pesée et payée, **datée de la réception** ; `Article.nature` =
libellé de la composition ; `Article.couleur` = libellé de la couleur sinon son code ;
`unite_commande`/`contenance_commande` vides si l'unité d'achat est le kg ; `FilMonte.poids_bobine`
= poids pesé du dernier lot sorti vers les machines, sinon du dernier reçu (M43) ;
`PlanQualite.depuis` = `depuis` de la dernière version, sinon le jour du premier mouvement ;
`Donnees.soldes` = (référence, lot, magasin) → kg ; `Parametres.cours` = la table des devises.

## 2. Points d'entrée

Une requête du pilotage fait, dans cet ordre (c'est ce que faisaient les routes de Gestion MP) :

```python
d = a_la_date(complet, jour, aujourdhui=aujourd_hui())   # = charger_au de Gestion MP
lignes = etat_stock(d, jour)                               # list[LigneStock]
plan = plan_achat(d, lignes)                               # PlanAchat
tableau = cockpit(d, jour, lignes, couts_rendus(d, lignes_recues, revient_par_reception(d)),
                  meme_couleur=True)                       # Cockpit (dataclasses)
ctl = controler(d, lignes, jour, complet=complet, aujourdhui=aujourd_hui())
note = synthese(ctl)
```

| Module | Points d'entrée |
|---|---|
| `a_la_date` | `a_la_date(donnees, date_ref, aujourdhui)` (montage inconnu avant aujourd'hui, soldes à None, bons rouverts) |
| `plan` | `plan_mensuel`, `m2_passe`, `plan_en_vigueur`, `m2_du_mois` |
| `nomenclature` | `nomenclature`, `controle_recettes`, `kg_par_m2`, `poids_du_role` |
| `besoins` | `besoins_mensuels`, `besoins_passes`, `besoin_sur_fenetre(…, *, jours_du_mois, prolonger)` |
| `stock` | `etat_stock`, `LigneStock` (70 champs de Gestion MP), `fils_en_machine`, `stock_en_machine` |
| `achats` | `echeance_commande`, `pas_partie(commande)`, `reste_a_livrer`, `montant_ligne_mad` |
| `plan_achat` | `plan_achat`, `tier` |
| `valorisation` | `couts_du_journal` (`.unitaire`, `.stock`, `.consommation`, `.cmup()`), `cmup_par_reference`, `valorisation` |
| `prix`, `opportunites` | `prix_constates`, `achats_dates`, `historique_prix`, `couts_rendus` (lignes reçues → `CoutDate`), `matrice_prix`, `comparer_les_prix`, `opportunites` |
| `pilotage` | `cout_matiere_annuel`, `cockpit`, `concentration_devises` |
| `fournisseurs` | `performance_receptions`, `scorecard_fournisseurs`, `points_score`, `devises_pratiquees` |
| `receptions` | `pesees`, `evolution_bobines`, `ecart_bobine` |
| `lots` | `stock_par_lot`, `lots_disponibles`, `tracabilite` |
| `production` | `consommation_par_of`, `ajuster_ordre` (→ `OrdreAjuste`), `realise_par_qualite`, `prevu_de` |
| `importations` | `revient_dossier`, `tva_attendue`, `ecart_droits`, `ecart_facture`, `lignes_aberrantes`, `lignes_negatives`, `revient_par_reception`, `revient_par_lot` |
| `inventaire`, `suivi`, `analyse_revient` | les calculs que Gestion MP faisait dans ses routes (écarts d'inventaire valorisés, tournant, échéancier, bilan du mois, photo des indicateurs, statut de livraison, analyse du coût de revient, coût d'une qualité) : la route lit la base, remplit les dataclasses d'entrée, appelle la fonction |
| `classification` | `decomposer`, `composer(composition, *, …)`, `designation` |
| `controles` | `controler(donnees, lignes_stock, date_ref, complet=None, aujourdhui=None)`, `synthese`, `REGISTRE`, `COLONNES`, `stock_negatif_passe` |

Les dicts de Gestion MP (cockpit, réalisé, consommation d'un ordre, évolution des bobines,
écart de facture, traçabilité, contrôle des recettes, synthèse) sont des **dataclasses aux
mêmes clés** : `dataclasses.asdict` (ou le schéma Pydantic de la route) redonne la même forme.

### Calculs des routes (`inventaire`, `suivi*`, `analyse_revient*`)

| Route de Gestion MP | Fonction PRO | Entrées à remplir par le service |
|---|---|---|
| `api/inventaires.inventaire_dict` (lignes, totaux) | `inventaire.ecarts_inventaire(lignes, *, statut, tolerance, couts, ajustements)` | `LigneInventaire` ; `couts = couts_inventaire(donnees)` ; `ajustements` = (lot, magasin) → n° du mouvement d'ajustement de l'inventaire (hors annulations) |
| `api/inventaires.a_compter` (tournant) | `inventaire.a_compter(stocks, *, classes, derniers, magasins, aujourdhui, magasin_id)` | `StockAuMagasin` ; `classes` = classe ABC du jour (`etat_stock`) ; `derniers` = date du dernier inventaire **validé** compté, par (matière, magasin) |
| `api/suivi._factures_dues`, `echeancier` | `suivi.factures_dues`, `suivi.echeancier(factures, frais, dues, *, taux, aujourdhui, du, au)` | `PeseeFacturee`, `FactureAPayer`, `FraisAPayer` |
| `api/suivi.photographier_indicateurs` | `suivi.indicateurs_du_cockpit`, `suivi.photographier_indicateurs(donnees, jour)` | — (OTIF moyen sur 12 mois, comme le code actuel) |
| `api/suivi.bilan` | `suivi_bilan.bilan(donnees, *, annee, mois, aujourdhui, mouvements, fabrications, commandes, receptions, ordres)` | tout le journal de la base par id croissant (`MouvementBase`), fabrications, bons, réceptions, ordres ajustés (`ajuster_ordre` au taux de perte de l'époque) |
| `api/achats._statut_livraison`, courriel du lundi | `suivi_livraison.statut_livraison`, `commandes_en_retard` | `BonALivrer` ; `recu`/`bloque` = `chargement.recu_par_ligne` et quarantaine au prorata |
| `api/analyse_import.analyse_revient`, qualité | `analyse_revient.analyse_revient(donnees, FiltresRevient, *, types_fil, ids_dossiers)`, `analyse_revient_qualite.analyse_qualite` | `ValueError` → 400 (axe, sélection) ou 422 (statut) ; `QualiteInconnue` → 404 |

Ces fonctions reçoivent les statuts **de la base** (minuscules : `validee`, `brouillon`,
`annulee`, `refuse`, `valide`, `soldee`…), rendent des `date` (l'API sérialise) et cherchent les
coûts par **n° de mouvement** : les `Mouvement.id` du moteur doivent être ceux de la base. Le
masquage des prix pour l'alimentation reste au filtre générique des routes.

### Contrôles (`calcul/controles/`)

Registre : `@controle("C08", gravite=…, lien=…, colonnes=(…), garanti="…")`, une fonction par
contrôle `(Contexte) -> (libellé, lignes)`, ordre C01…C38. Chaque `Controle` porte `code,
libelle, anomalies, detail, gravite, garanti, quoi_faire, lien, colonnes` (route 212 d'API-PRO :
`lignes` = `detail`). Le détail est **complet** (plus de troncature à 200 : la route pagine) ;
les colonnes ont une unité (`kg`, `m`, `MAD`, `%`, `j`, `date`, `texte`, `nombre`) ; tout écart
relatif est une **fraction** (C08, C30, C35, C36). Libellés et gravités : ceux du **code** de
Gestion MP, là où ECRANS-PRO § Contrôles diffère (C06, C10 bloquant, C11, C15, C23
avertissement, C25, C28, C29, C31, C34, C36) — le coordinateur peut mettre ECRANS-PRO à jour.
Les intégrités (C12, C14, C27, C37) tournent sur `complet` (toutes les données, soldes compris).

## 3. Cache

Le moteur ne garde rien entre deux appels, sauf `Donnees.derniere_date` (mémo de `a_la_date`,
valable tant que l'objet n'est pas modifié en place). Le cache est à **S4**
(`services/donnees_moteur.py`, ARCHITECTURE § 7) : `Donnees` complètes gardées par processus,
clé = signature **lue en base** à chaque appel (`jour`, `max(journal.id)`, `max(mouvement.id)`,
`max(parametre.modifie_le)`, `count(mouvement)`, `Σ solde.quantite`). Les objets rendus par
le moteur partagent des listes avec les `Donnees` (`a_la_date` les copie superficiellement) :
**ne jamais modifier en place** des `Donnees` mises en cache ni ce que le moteur en tire.
Ordres de grandeur sur l'année d'essai (10 411 mouvements, 124 matières) : `etat_stock` 16 ms,
`couts_du_journal` 19 ms, `cockpit` 28 ms, `controler` 29 ms ; une route qui appelle plusieurs
fonctions partage `lignes` (et, si besoin, `couts_du_journal`) plutôt que de les recalculer.

## 4. Vérification (pour R2, V1 et les lots D)

- `tests/moteur/` : un fichier par module (essais hérités de Gestion MP avec « Hérité : … »),
  un essai par contrôle, essais de propriétés (`test_proprietes.py`, hypothesis : lots = stock,
  jamais sous zéro, valeur conservée, annulation au coût de l'original, sortie annulée neutre,
  date passée indépendante de la suite).
- **Parité unitaire** (`test_parite_unitaire.py`) : 20 jeux de `Donnees` réels (année d'essai
  de l'ERP Fil importée par Gestion MP), à 20 dates et périmètres (`tests/moteur/jeux/*.json.xz`,
  7 Mo), et leurs 39 sections de sorties produites **une fois** par le moteur de Gestion MP
  (`backend/essais/gestion_mp_calcul.py`, lancé par `~/gestion-mp/.venv/bin/python`). Égalité
  **exacte** des nombres. Seuls écarts ramenés (voulus) : détail des contrôles non tronqué, C35
  en fraction. R2 peut réutiliser `tests/moteur/jeux_outils.py` (relecture d'un jeu en `Donnees`
  PRO, mise à plat, comparateur) et `sorties_pro.py` ; S4 peut vérifier `charger_au` en
  comparant ses `Donnees` à celles d'un jeu.
- Limites des jeux réels (couvertes par les essais à la main) : aucun fil monté, aucune version
  de plan, aucun ordre au prévu figé, aucune commande soldée à la main, annulée ou avec ETA,
  aucune répartition de frais figée.
- Régénérer les attendus après un changement voulu du moteur de Gestion MP :
  `~/gestion-mp/.venv/bin/python backend/essais/gestion_mp_calcul.py calculer jeux/NN-x.json.xz
  jeux/NN-x.attendu.json.xz` (et mettre à jour `COMMIT_GESTION_MP` de l'essai).
